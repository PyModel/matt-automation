# Build: stage 7, the task graph

Load implement-spec by path and run it as the orchestrator with the bindings below. Read PIPELINE.md § Isolation and § Budgets and CONTRACT.md first. `node ROOT/scripts/goal.mjs registry <slug> building`. Record each ticket's starting point `<ticket-base>` on dispatch; the whole deliverable is diffed against `review_base` (BOOTSTRAP.md § 0c). Done per PIPELINE.md § Completion criteria per stage (7).

## Bindings to implement-spec

- **Step 2, exploration subagent:** one, writing notes for the whole graph into `<state>/runs/<slug>/notes/`, external lookups via `research-stack`.
- **Step 3, branch and PR:** local tracker (default): no PR, the run branch is the integration point. GitHub tracker, push authorized: one draft PR closing the spec and every ticket.
- **Step 4, implementers:** one per frontier ticket, each in its own worktree and branch (PIPELINE.md § Isolation), dispatched only while the budgets allow (PIPELINE.md § Budgets) and `STOP` is absent. Local tracker: take tickets with `node ROOT/scripts/goal.mjs take <feature> <free slots>`, which reads the frontier and flips the tickets to `in-flight` in one locked transaction, so two orchestrators never take one ticket. GitHub tracker: read the frontier and set the issue's status inside `goal.mjs with-lock frontier-<feature> -- <gh commands>`. Parallel only when claims are disjoint (stage 6b guarantees this for `ready-for-agent` tickets). Per taken ticket, before dispatch: create its worktree, re-check CONTRACT.md § Readiness, compile its contract to `tickets/<NN>.goal.md` (CONTRACT.md § The contract) and check it with `node ROOT/scripts/goal.mjs contract tickets/<NN>.goal.md --worktree <ticket worktree> --ticket <ticket file>`, which must exit 0 before this and every later dispatch of the ticket, and pick its worker from its capability (`goal.mjs frontier` reports it; NOW `tiers:` maps it). Record each dispatch in NOW and Events.
- **Step 5, merger subagent:** per ticket back from its implementer, the orchestrator saves the implementer's final message to `tickets/<NN>.receipt.md`; then, as one `goal.mjs with-lock integration -- <merge script>` transaction:
  0. CONTRACT.md § The receipt check. A refused receipt, or any conclusion but `completed`, stops here: a `claims-breach` receipt goes to § Claims amendment, any other to § Stuck detection with the check's `problems` or the receipt's `blockers`.
  1. `node ROOT/scripts/goal.mjs claims <ticket file> $(git diff --name-only <ticket-base>...HEAD)` (on a GitHub tracker, the ticket file is the issue body saved with `gh issue view <n> --json body -q .body`). A nonzero exit (an `unclaimed` path, or a `guarded` path without an explicit grant) is an **unclaimed edit**: the implementer changed a path without reporting a breach. The merger rejects the ticket, and it is a stuck signal (§ Stuck detection); a path the ticket legitimately needs is added by § Claims amendment before that re-dispatch.
  2. Rebase the ticket branch onto the run head; for `shared-regenerate` conflicts run the regenerate command and take the result; other conflicts → `resolving-merge-conflicts` (never `--abort`), then re-run the suite and a single-agent review of the resolved hunks.
  3. `merge --ff-only`, record the ticket as the range `<before>..<after>` on the run branch (pre-rebase SHAs in status files are historical only), remove the worktree and branch. A rebase that changed the ticket's diff (a resolved conflict) needs a fresh receipt at the rebased head before step 6, since `status … done` compares what landed with what the receipt proves.
- **Step 6, frontier:** after every merge the orchestrator checks the receipt's `external_effects` against the objective's grants (an ungranted one is a blocker), sets it done (`goal.mjs status <feature> <id> done --landed <after>` on the local tracker, which re-checks the committed receipt against git, confirms `<after>` carries that change, and ticks the boxes; the issue's status on GitHub), updates `todo.md` and the ledger and commits them with `goal.mjs commit`, and in flat mode runs `code-review` for that ticket's range `<ticket-base>...HEAD` itself; then takes tickets again for the freed slots. That review's cited findings sit in this run's own diff, so they are introduced by this run (§ Bugs found in flight, item 2) and never spend the bug-ticket budget, which counts only pre-existing bugs. Each one is fixed in a fix ticket (carrying `**From review:** <NN of the reviewed ticket>`) with the finding's red test as a criterion, or added to a ticket that has not been dispatched, widening its Claims line if the fix needs more files (committed with `goal.mjs commit` and the finding as the reason; `take` re-runs the claims gate before it can start), and that ticket then passes the PLAN.md 6b gate again. A ticket already in flight or done never gains criteria. Review-fix depth: a ticket that itself came from a review (a fix ticket) gets its own review, but only its high and medium cited findings become a new fix ticket; its low findings and test gaps go to NOW `leads:` for the stage 8 final review. A fix ticket of a fix ticket is the last generation: its review's findings all go to `leads:`, so no review→fix chain runs deeper than three tickets; `goal.mjs frontier` reads the `**From review:**` chain and reports a deeper ticket as malformed, so `take` refuses it. Fix-ticket criteria state observable behaviour (PLAN.md 6b), never the mechanism of the fix. Uncited leads go into NOW `leads:`.
- **Step 7, single fix subagent:** used in CLOSE.md stage 8, not here.
- **Step 9, cleanup:** every ticket worktree is removed at merge; a sweep at the end of stage 7 confirms only the run worktree remains.

## The implementer brief

The brief is the contract file `tickets/<NN>.goal.md` (CONTRACT.md § The contract), plus, verbatim: the implement file's contents, the guards from PITFALLS.md, this list of rules, the receipt format (CONTRACT.md § The receipt), and LEDGER.md § Subagent contract last. State the ledger holds stays in the ledger; the contract points at it.

1. Apply the per-worktree recipe (ports, `.env`, data dir), run the install command, run the single test file for the seam before touching code.
2. For every slice call `tdd`: one failing test at a pre-agreed seam, watch it fail, minimal code, watch it pass; typecheck and run the single test file after each slice; browser tests only after the behaviour works. No test at an unagreed seam.
3. Call `defensive-design` in Implement mode for the ticket's tier: its required tests and an evidence state per control (verified / reasoned_not_run / blocked / not_applicable) written into the status file.
4. A red test that will not go green for a reason the ticket did not predict → `diagnosing-bugs` before changing course. The same non-quarantined test failing 5 times, or the per-ticket slice or time cap reached → stop, mark the ticket `stuck` in the status file with the reason and the loop output, return a `stuck` receipt. Check `runs/<slug>/STOP` before every slice; present → finish the slice, commit, return a `stopped` receipt.
5. Touch only claimed paths. Before the first edit, list every file the change forces: implementers, conformers, fakes and mocks of any interface, protocol or message you change, field-by-field mappers and copies of any type you extend, and their tests. Any of them outside the claims → return a `claims-breach` receipt now, naming all of them in `blockers`, each with why. A forced path found later → stop the slice, record it in the status file, return a `claims-breach` receipt naming every path still missing.
6. Run the full suite once at the end; compare per test id against the baseline set (quarantined tests ignored): no test that passed at base may fail now. Commit with `Refs <ticket id>`, then run every validation command the receipt will list through `node ROOT/scripts/goal.mjs run -- <command>` on the clean, committed tree and cite the `log` it prints; a criterion's evidence names the validation command that shows it, then review: in `nested: yes` mode call `code-review` against `<ticket-base>...HEAD` (the whole ticket range) with the ticket path as spec; in flat mode do one inline pass over the full ticket diff on both axes yourself. Fix cited findings; verify each fix against the ticket seam; uncited leads go in the status file. End with the receipt: every criterion with its evidence, the worktree committed and clean.
7. Human-only step → `wizard`, script path in the receipt's `blockers`.
8. Heartbeat: update `tickets/<NN>.status.md` before and after every slice and before any command expected to run longer than a minute (install, suite) with `heartbeat: <output of date +%FT%T%z>` (the real clock, never estimated), `agent: <id or pid>`, `active_cmd: <name if active>`, `slice: n/m`, last commit, suite result; commit it with `goal.mjs commit`. Skills you may load: `tdd`, `defensive-design`, `diagnosing-bugs`, `code-review` (nested mode only), `wizard`.

## Implementer backend

NOW's `worker:` picks who runs the implementer brief. Default `subagent`: the harness's own subagent, as above. `pi[/<provider>/<model>]` (named in the objective or answered by `/kun`): each ticket's brief goes to a pi worker through to-orc's dispatcher, which proves the model that ran and bounds the ticket by its cycle and cost caps:

```
node ROOT/scripts/goal.mjs dispatch <slug> <NN> --worktree .worktrees/goal-<slug>-t<NN> -- \
  --phase implement --task impl --background --brief <brief file> [--model <provider>/<model>]
```

`dispatch` refuses a ticket that is not in flight or whose committed contract fails the `contract` checks, and sets `--run-dir` to the ticket's own `d=<git-common-dir>/to-orc/<slug>/t<NN>` and `--repo` itself; never call `orc-dispatch.mjs` directly or pick another run directory. Before the first dispatch write `$d/accepted/scout.md` and `$d/accepted/research.md` citing `findings.md`, `spec.md` and the notes dir: stages 1–5 did that work. The brief file is the contract plus the rest of § The implementer brief; `--model` comes from NOW `tiers:` for the ticket's capability, else NOW `worker:`. Poll with `goal.mjs dispatch <slug> <NN> --worktree <wt> -- --poll --task impl`. `COMPLIANT` hands the ticket to step 5, whose receipt is the worker's final message (CONTRACT.md § The receipt); any other `orcStatus` is a stuck signal for § Stuck detection, with the status file's `reason` appended to the re-dispatch brief. `COMPLIANT` proves the dispatch, never the ticket: only the receipt check does.

**One budget per ticket.** The run directory's cycle cap (`--cycles`, default 2) is the ticket's whole implement→repair budget: a claims-breach re-dispatch, a repair after a refused receipt, and a pre-merge review repair all spend it. A pre-merge review finding (a review the objective requires before each merge) goes back as a `repair` dispatch in the same run directory; its receipt still lists every ticket criterion verbatim and puts the findings in `repairs` (CONTRACT.md § The receipt). When the cap is spent, remaining findings become a fix ticket with `**From review:** <NN>`, or the ticket goes `stuck` with its reason; a fresh run directory for the same ticket is never the way round the cap.

## Stuck detection

Separate heartbeat liveness, active command execution, and completed-slice progress. A dispatched ticket is **stuck** when any of: its receipt is refused or its conclusion is `partial`, `blocked`, or `stuck`; the merger finds an unclaimed edit; its `heartbeat` is older than 30 minutes and its `agent` is not alive; its `slice` counter is unchanged across 3 heartbeats while no command is running; its status file reports the same non-quarantined test failing 5 times; the per-ticket slice or wall-clock cap in NOW `budgets:` is reached (`stuck: too big`, the lever is upstream: it should have been split); or the harness reports the agent gone.

Before any re-dispatch: revoke the old lease, send cancellation (SIGTERM, then SIGKILL if needed) to the PID the dispatch recorded, never by name or pattern (PITFALLS.md), and wait for confirmed process termination so two writers never share a worktree. Stuck once → record, re-dispatch from the status file with the failure appended to the brief. Stuck twice (the re-dispatch budget, which only stuck signals spend; § Claims amendment dispatches are capped separately by `goal.mjs claim`, at two per ticket) → `goal.mjs status <feature> <id> stuck -- <reason>` and mark it in `todo.md`; mark dependent tickets `blocked: prerequisite <id> stuck`; continue the rest of the graph; it is a blocker in the report. Never a third stuck dispatch.

## Claims amendment

A `claims-breach` receipt is the implementer doing the right thing: it stopped before touching an unclaimed path. It is not a stuck signal and spends none of the ticket's re-dispatch budget. For the paths its `blockers` name:

1. Local tracker: `node ROOT/scripts/goal.mjs claim <feature> <NN> exclusive <path>... -- "<why>"` (`shared-regenerate` for tool output). In one commit it adds the paths to the tracker issue's Claims line and the contract's, records a `**Claims amended:**` line on the ticket, and logs a `[claims]` event. It refuses, changing nothing, when a path is guarded, whether declared `guarded` by any ticket or in a guarded class (`.github/`, CI config, a `migrations/` directory, any top-level file), since only the objective's grant authorizes it and so it is a blocker, when the path would overlap an unordered open ticket of this run, and on a third amendment of one ticket. Its `cross_run` output goes into NOW `leads:` as for PLAN.md 6b. GitHub tracker: make the same checks by hand, then edit the issue's Claims line and the contract inside `goal.mjs with-lock frontier-<feature>`.
2. Refused for an overlap → add a blocking edge or split the change into a new ticket through the PLAN.md 6b gate, and re-scope this ticket so that it no longer needs the path. Refused as a third amendment → the ticket is mis-scoped: mark it `stuck: mis-scoped` and split it at 6b.
3. Dispatch the ticket again from its status file, the amendment appended to the brief. The contract and the tracker now agree, so the receipt and claims checks read the widened claims.

Never edit a Claims line by hand once the ticket is dispatched; `goal.mjs commit` refuses it, and `contract` catches a raw commit.

## Bugs found in flight

No deferred actions. Any bug, error, or anomaly noticed in any file, by any agent, at any stage:

1. **Record now:** `bugs.md` and a `[bug]` event: file, symptom, how noticed, introduced by this run or pre-existing. A test that passed every baseline run and now fails, even once, is introduced by this run until shown otherwise. It becomes pre-existing only when it also fails at the base commit under the same conditions (the same full-suite load, as many runs as it took to fail here), with the command and count recorded; passing when run alone proves nothing.
2. **In scope or introduced by this run** (touches a claimed path, or was not present at the branch point): fix now, red regression test first, same ticket branch; `diagnosing-bugs` if the cause is not obvious.
3. **Pre-existing and out of scope:** open a ticket now (`bug`, `ready-for-agent`, repro, claims). Ask `/kun` whether this run builds it; yes and the bug-ticket budget allows → it passes the PLAN.md 6b gate and then joins the frontier; otherwise it stays ticketed for the next run with its id in the report. Either way it is never a comment, TODO, or "known issue".
4. **Cannot be fixed by this run** (authority, credentials, human-only): blocker in NOW and the report, with the ticket id.

Debt markers, temporary workarounds, swallowed exceptions, and disabled or focused tests are prohibited in the diff; `code-review` cites them. The mechanical part is this grep, over added lines only so that deleting old markers succeeds; it must be empty:

```
git diff -U0 <review_base>...HEAD | grep '^+' | grep -v '^+++' | grep -nE 'TODO|FIXME|HACK|XXX|\.skip\(|\.only\(|\bxit\(|\bxdescribe\('
```
