Context window: LEDGER.md § Compaction and context pressure. Each stage is done per PIPELINE.md § Completion criteria per stage. `goal.mjs registry <slug> specced` after stage 5b and `ticketed` after 6b.

1. **Route.** Explore the repo first, no external lookup: `CONTEXT.md`, `docs/adr/`, `docs/agents/*.md`, seams, test conventions, the failing command if one is named, and the tracker and `tracker/` for overlapping work. Walk FLOWS.md § Routing tree over the ask-matt map read at stage 00 and classify the objective. Output the route, an adopted-patterns list (each line naming its skill; open a skill's file before adopting any load-bearing claim about it), and the research need per FLOWS.md § Research need. Write `findings.md`: repo-sourced facts, numbered requirements R1…, and open external questions Q1… (one API, one behaviour, one version claim each). A `greenfield` classification switches to the `to-new` overrides (`ROOT/to-new/SKILL.md`); a `bug` classification arms § Bug fast path below; a `ready` classification takes § Ready source below.
2. **On-ramp (conditional).** Run what stage 1 chose, self-answered per KUN.md: `triage` (raw issues), `diagnosing-bugs` (something broken; runs in the run worktree; the loop goes red before any theory), `wayfinder` (fog; merges at stage 5 as `to-spec <map path>`; the local tracker template carries its "Wayfinding operations" section, verified; it spawns `research` per research ticket itself), `improve-codebase-architecture` (upkeep, no target), `zero-tech-debt` (refactor of a named area; its pre-flight and end-state paragraph seed the grilling). 3. **Research (conditional).** When the research need is `none` and `findings.md` has no open Q, log `research: skipped (no external unknown)` and continue. Otherwise load `research-stack` and call `research` once per open Q, briefed per PITFALLS.md (research rows). Append sourced facts to `findings.md`, close each Q, promote settled facts to R<n>. Any later stage or subagent that hits an external unknown does the same on demand, with one line in `log.md`.
4. **Grill.** Load grill-with-docs (it calls `grilling` and `domain-modeling`; confirm both loaded). Run the rounds with KUN.md § Grilling rounds. Facts a round needs come from sub-agents, not questions. For each new module or seam call `codebase-design` and run design-it-twice. For every module the objective touches call `defensive-design` in Design mode once: consequence tier 0–3, contract, smallest proportional controls in a failure→consequence table; Tier 2/3 get its checklist sections and, at any security-sensitive boundary, the secure-coding overlay. When the deliverable is a skill or an agent-facing doc, `writing-for-agents` is the standard. When only a named person could answer, load to-questionnaire, write the file, continue with the default. Terms go into `CONTEXT.md` as they settle, committed as their own commit `[<slug>] glossary` at the head of the run branch so cross-run merges conflict only there (the report lists glossary deltas); an ADR only when hard to reverse, surprising, and a real trade-off. Name the test seams: the highest existing seam, ideally one; they go into the spec's Testing Decisions and every ticket brief.
   **4b. Challenge gate.** The challenger half of KUN.md § Grilling rounds; done per PIPELINE.md (4/4b).
5. **Spec.** Load to-spec. Synthesize from stages 1 to 4 only. Seams into Testing Decisions; the defensive tier and controls table per module into Implementation Decisions; the tier's required tests (malformed input, negative authorization, duplicates and races, cancellation and restart, as applicable) into Testing Decisions. Publish to the tracker from stage 0b (PIPELINE.md § Tracker rules), `ready-for-agent`; write the working copy `runs/<slug>/spec.md` whatever the tracker, so to-tickets never re-fetches.
   **5b. Reconciliation gate.** A subagent with only `log.md`, `findings.md`, and the spec lists every logged answer and requirement that is missing from the spec or softened (a number became "reasonable", a negative requirement became silence, an ordering guarantee became prose). Fix the spec for each; re-run the gate until the list is empty. Log the gate's output.
6. **Tickets.** Load to-tickets, pointed at the spec path. Local tracker: one file per ticket, numbered blockers-first. Every ticket carries a demo-path line (3–7 tickets by default; merge any ticket with none), its module's defensive tier, and a **claims** list in three classes (CONTROL.md § Tracker grammar): `exclusive` paths it will create or modify; `shared-regenerate` files every ticket touches through a tool (lockfile, codegen output, snapshots, registries), which the merger regenerates with the `commands:` regenerate entry instead of treating as a conflict; `guarded` paths (CI workflows, top-level config, migrations), which only the objective's explicit grant authorizes (SKILL.md § Rules, Autonomous). Claims come from the stage 1 exploration and the spec's module list; in a monorepo, prefixed by package. Prefactoring tickets are scoped with `zero-tech-debt` (pre-flight, one coherent end state) and come first. Self-quiz (granularity, edges, merge/split) via KUN.md. Every ticket also carries a `**Capability:**` line (CONTRACT.md § Capability). Strip `ready-for-agent` from the parent spec after publishing.
   **6b. Criteria and claims gate.** For every acceptance criterion describing new behaviour or a bug fix, name the observation that would show it false and confirm it fails at the base commit (run it with the test patch against base; a missing test file is not behavioural red). Criteria asserting preserved invariants, security guarantees, or existing compatibility must stay green at base; never invert a valid invariant to force a red result. For every pair of tickets, intersect their `exclusive` claims (`shared-regenerate` never conflicts); overlapping tickets get a blocking edge or a merged scope. Every ticket passes CONTRACT.md § Readiness (its base is the run branch head for now; dispatch re-checks it); a ticket that fails is rewritten until it passes. Every ticket that enters the graph later (a bug ticket from BUILD.md) passes this same gate before it can be `ready-for-agent`. Write the ticket table (blockers, claims, status `blocked`/`ready-for-agent`) into `todo.md`. Local tracker: `node ROOT/scripts/goal.mjs frontier <feature>` exits 0 (no malformed ticket, no overlap). GitHub tracker: check the same two rules over the issues' Status, Blocked-by, and Claims lines.

## Ready source (route `ready`)

Stages exist to produce an agent-ready source; when the objective already names one, they are skipped, not re-run. Applies when the objective points at an approved spec, ticket, or tracker issue this repo holds (a path or a full reference), and that source passes CONTRACT.md § Readiness as a whole, bar the base (stage 0c recorded `review_base`). A raw issue someone else filed is triaged first (FLOWS.md row 1); a label alone never makes a source ready.

- Stage 1 still explores the repo and writes `findings.md`; every requirement in the source becomes an R<n>.
- Stages 2 to 4b are ticked `(skipped: ready source <path or ref>)`. Research runs only if `findings.md` has an open Q.
- Stage 5 copies the source into `spec.md` verbatim, with a header naming where it came from, and publishes it to the tracker as the parent. 5b runs as written, reconciling against `findings.md`.
- Stage 6: a source that is one ticket becomes ticket `01` as it stands, plus its claims, capability, and demo path; a spec goes through to-tickets as usual. 6b runs as written.
- Any readiness box that fails turns this path off: log which one, and the run continues at stage 2 with the source as its first finding.

The bug fast path below is the same move for a finished diagnosis.

## Bug fast path (route `bug`)

Applies when `diagnosing-bugs` finished with: one command red before any theory, a regression test red then green, a named seam, a post-mortem, and the fix confined to modules that fit one `exclusive` claim set at Tier 0 or 1. Then stages 4 to 6 are skipped:

- `spec.md` is the post-mortem: symptom, red command, root cause, seam, regression test path, tier, files touched. Publish it to the tracker as the parent.
- Exactly one ticket `01`: acceptance criterion = the regression test command; demo path = the red command going green; claims = the files the fix touched; tier from `defensive-design` Implement mode over the diff; capability from CONTRACT.md § Capability (no line means `standard/medium`). Run the 6b gate (the criterion is red at the base commit by construction; verify by running it there).
- Stage 7 has nothing to dispatch: write ticket `01`'s receipt from the on-ramp's own evidence, check it with `goal.mjs receipt` against the run worktree and `review_base`, record ticket `01` as merged with the commit range the on-ramp produced on the run branch, run the full suite against the per-test baseline, tick the ticket, and go to stage 8, whose diff from `review_base` includes the stage 2 fix.

Any of these turn the fast path off and the run continues at stage 4 with the post-mortem as its first finding: no seam found, more than one claim set, Tier 2 or 3, a `guarded` path, the regression test needs a fixture the repo lacks, or the post-mortem names a design cause (`improve-codebase-architecture` lead). `/to-bug` pins this route and skips the classification.
