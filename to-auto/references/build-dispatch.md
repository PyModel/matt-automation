# To-auto build dispatch

- Pass absolute paths to `goal.mjs` subcommands (`contract`, `receipt`, `claims`, `commit`) when the cwd is the target repo. Relative `runs/<slug>/...` paths resolve against the repo and fail with ENOENT. `commit` takes file paths only: a directory argument fails with `EISDIR`, so glob the files (`$S/tracker/$SL/issues/*.md`) and check the exit with `&&`. zsh does not word-split an unquoted variable: a newline- or space-joined `FILES=$(ls …)` reaches `commit` or `rm --cached` as one pathspec. Build a zsh array (`rel=( ${files[@]#$C/} )`) and pass `"${rel[@]}"`.
- Get run and ticket worktrees only from `goal.mjs worktree get <slug> [NN]`. Never type `git worktree add` by hand.
- Before each landing, confirm the `wt-NN` file the merger reads for that ticket's worktree path is staged for this run. A landing run without it fails; M4 t01/t11/t05 had to be re-staged and re-landed for that reason.
- Check each `goal.mjs` result is its real output before writing a dispatch file or contract from it. A result reading `(eval):N: no such file or directory: node …/goal.mjs` means nothing ran: zsh did not word-split a `$G` variable. Use the `g()` function from `to-auto-ticket-lifecycle` 5i, and never pipe the call through `tail` before the file write.
- If the isolation guard denies a Bash call that writes a script or brief containing worktree text, reword the text and retry once. Do not route around the guard with a different worktree command.
- Before dispatching an implementer, confirm the contract check passes on the exact ticket file the brief cites.
- A passing `contract` check does not prove the claims are complete. Before dispatch, `test -e` every claimed path, and grep the tests and generated outputs for each literal the change alters (enum lists, `len == N` assertions, SQL LIMIT values, and assertions on a navigation destination or enum case the change moves); claim every file that hits, including generated output. (2026-10-17 M4 t08: GuestFlowTest's old `SignIn()` destination assertion and CheckoutSheet lifecycle effects surfaced only after the first edit, although the brief carried a forced-path audit.) A missing forced path means the implementer stops at claims-breach before its first edit, costing a whole dispatch round. Run every grep criterion against the base tree before dispatch. A criterion that counts compiler or test output (opt-in warnings, `--tests` selectors, golden or testcase counts) is not a grep: compile the test source set at base (`:compileDevDebugUnitTestKotlin --rerun-tasks`-style) and claim every file it names, plus each fixture or helper those tests import (2026-10-17 M3 t11: the base compile printed 32 `ExperimentalRoborazziApi` lines from 5 files, two unclaimed, and a test asserted a placeholder title; the ticket breached at orientation after both amendments were spent, and its successor carried the four forced paths). A pattern that prints 0 at base and head is mis-specified, so fix the literal first (2026-10-16 t02: `"ContractTest"` never matches the fully-qualified class name in the manifest). For a move or rename ticket, grep docs (`docs/`, ADRs, READMEs) for links to the old path and claim those docs in the same ticket; an unclaimed link goes stale (2026-10-16 t02: ADR-0043 still linked the moved build script, found only after dispatch and routed to a later ticket).
- After a claims-breach, amend the ticket's claims, rebuild the brief from the amended contract, and append the implementer's first-pass leads to the brief before re-dispatching. If the implementer is still resumable, send it the amended claims with SendMessage instead: it keeps its context and no dispatch round is spent (2026-10-16 t08 resumed with context intact).
- Carry helper scripts into a new run on the same branch chain from the previous run's `notes/scripts/`: `sed -i ''` (macOS) the old slug, run id and port block, pool number, baseline count and review base sha, and the read-only path list into each copy. Copy the baseline's counting scope from the prior ledger `- baseline:` line: a re-pinned count of a different scope is not comparable and reads as a regression (2026-10-17 Android follow-up: the M4 ledger said `11808 test ids: android 2575 testcases across three flavors + api`, the re-pinned line said `1,462 android test ids (dev flavor + :api)`, so the two numbers were changed to the same scope before the baseline ran). Then `grep -n '<old-slug>\|pool/<old>/'` over the destination must print nothing before the first merge. Keep the copies under the run's `notes/`, not the scratchpad. Dispatch prompts go there too: write each Agent prompt to `runs/<slug>/notes/dispatch-<NN>.txt` before sending it. A compaction then leaves the brief on disk; without that file the prompt had to be recovered by scanning the session JSONL for the Agent tool call.
- A claims amendment that adds a path an in-flight ticket already holds is not a second exclusive grant. Record `+path (exclusive)` with the reason, add a blocking edge on the holder, and let the breaching ticket resume after that landing. When a routed lead or a deleted helper will force paths outside the claims (a composition root, a test helper other tests import), grant them in the same amendment before dispatch so the implementer does not spend a breach round on them.
- Device-gated criteria (emulator, phone, device-only UI): before dispatch, probe the device on this host (emulator accel check, then a headless boot capped at 60 s). If the probe fails, mark those criteria `blocked: host` in the ticket up front and name it in the hand-back. Do not let an implementer discover it late.
- Before dispatching parallel tickets, intersect their claimed paths pairwise. Any shared path needs a blocking edge in the ticket order; an unordered overlap is caught here, not at landing. A ticket that reads a type, signal or config value another ticket introduces needs a blocking edge even with no shared path; a self-quiz found a misconfigured-state UI reading an identity signal from an unlinked earlier ticket. For each exported type, interface, or constructor a ticket changes, grep every fake, stub and conformer under `tests/` and claim each one that must change; an unclaimed stub fails only at the implementer's first run.
- Red-at-base check for bug and acceptance criteria before dispatch: copy the probe test into `tests/` temporarily, run it under the repo's pinned Node, save the per-criterion failure lines under `runs/<slug>/notes/`, delete the probe, and confirm `git status --porcelain` shows no new file. A criterion that passes at base is not a regression test; rewrite it before dispatch. Also grep each new test name the ticket adds (`grep -rl <name> <worktree>/apps/android`) at base: a hit means the name already exists, so its red is not new. Print the hit count per name, not just a "done" line. (2026-10-17 host-settings-mirror 6b: all four bug probes failed on assertions at base, none crashed.) A compile error is not a red: a base run that fails to compile in about a second ran zero tests and proves nothing about the assertion. Re-run until the runner reports the probe's own assertion failure with a test count, and quote that line in the criterion's notes (2026-10-18 M4 t01: `red run at base-code showed 2 failed (placementRulesRun`).
- Ticket that deletes code: for each behaviour the deleted code still provides, including a fallback that looks unreachable, add a criterion that passes at base and fails once the code is gone. A deletion without such a pin is a silent behaviour change (2026-10-17 one-auto-review-pipeline: deleting the `resolveTurnShellAutoReviewInputs` fallback would have stopped review of a run's remaining shell commands after shell review was switched on mid-run; the owner kept that behaviour and ticket 02 got a pin test).
- Before dispatch into pool worktrees, verify each payload directory is a real directory, not a symlink: `for d in node_modules .cache src/app/dist; do [ -L "$w/$d" ] && echo "SYMLINK $w/$d"; done`, then `diff -rq src/app/dist` against the owner checkout. A symlinked payload lets a test write into the pinned main payload. Clone with `cp -cR`. A fresh worktree without `node_modules` fails its first test or typecheck run: pre-clone the payload before dispatch, not after the implementer reports it missing.
- Before planning fan-out, probe nesting: ask one subagent whether its tool list has an Agent tool. If it has none, run flat: each implementer reviews inline on both axes in one pass, and the orchestrator runs the per-ticket review after merge (2026-10-16 probe: "no Agent tool in my tool list"). Subagents cannot spawn agents (spawn depth 1), so a reviewer brief whose loaded skill spawns agents (code-review's Standards and Spec passes) must say to run those passes inline and report each one separately; a brief that omits this leaves the reviewer blocked on nested dispatch.
- Brief every implementer: one heredoc or file write per Bash call. Chaining several heredocs in one call hung one implementer 36 min with no child process and no tool result (2026-10-16 t01).
- Every reviewer and implementer brief forbids `git checkout` and `git switch` in the owner checkout (the borrowed main). Read other revisions with `git show <sha>:<path>`. A reviewer that switches branches leaves the owner checkout detached, and the next close-out inherits it.
- Write contract, brief and ticket files with a quoted heredoc (`<<'EOF'`), passing run values in as env vars or argv. An unquoted `<<EOF` expands backticks and `$` inside code snippets and silently drops them; a contract with a swallowed snippet was regenerated. After writing, grep the file for one distinctive line of each snippet.
- Design or explorer subagents: the brief's read list is a contract. The return must name every file read; a return that says it did not read a listed file is re-dispatched, not accepted (2026-10-17 design-it-twice agent skipped three of the brief's files).
- A subagent `BUG:` line is a hypothesis. Trace the callee before recording it in `bugs.md`. 2026-10-17: a design agent flagged "partial setHostSettings resets notifications"; `setNotificationConfig` (sand-settings-store.ts:343) ignores its input, so the entry became `not a bug` with that reason.
- Check every numeric acceptance floor against the axes it enumerates before dispatch. A floor above the product of its axes can never pass; fix the arithmetic or the floor. 2026-10-17 M3: a golden floor of 72 over 10 states × 6 was caught by the self-quiz, not by the implementer.
- A ticket that changes a type, signature or union: before dispatch, apply the prototype on a scratch copy of the tree and typecheck it. Record the error count and which files it hits; claim every file that fails, and let the ticket's criteria assert the expected error set. (2026-10-17 one-auto-review-pipeline run C: a typed-facade prototype typechecked with 0 errors, a misspelt row failed with TS2322, and all six affected test files passed, so the claims held.)
- Before dispatch, `grep` every run-specific fact the brief states (a file path, class name, `file:line` range, a group or test count) against the ticket worktree at base. Re-derive counts by script from the source tables, never from the spec's figure. Scout and research reports are leads too: re-check each "open" item at the base head before ticketing it, since some are already fixed and some inventory lines are wrong. A `No such file or directory` means the brief is wrong: fix the fact before dispatch. 2026-10-17 M4 t03: the brief placed `FileStorage` in its own `data/FileStorage.kt`; grep at base showed it is the class at `data/LiveAdapters.kt:109`, already claimed. The error surfaced only after dispatch and needed a mid-flight SendMessage correction.
- Quiet-machine hold: when a peer session needs an idle machine, write a `HOLD` marker in the run directory and tell the peer the dispatch time and expected release. Brief each implementer to run `test -e <run>/HOLD` before every Gradle, `go test`, vitest or pnpm command; while the marker exists it runs only git, grep, reads, edits, and tests-only commits. Remove the marker on the peer's release message or at the stated time, then run the gates. Extend a hold only after telling the peer before its release time. A hold wait is bounded by that release time, never by a poll count: an implementer that polls for a peer all-clear for its full window idles for the whole window. When the peer says the hold is no longer needed, or `uptime` shows low load, the orchestrator sends the implementer a release by SendMessage at once, naming the gates to run next. While a hold is active, each ticket's gate is the hold-safe subset (the repo's typecheck, comments check, and its gate test files); a full-gate criterion is not given to a ticket during the hold, and the full gate runs once at stage 7 on the merged head. Re-run `uptime` at each orchestrator turn while the hold is active; do not wait for a peer message that may never arrive.
- Never count warnings or testcases from a `-q` run: quiet mode hides the compiler lines, so a zero is not evidence. Every warning-count or test-count criterion runs without `-q`, and the brief says so beside the command.
- Scope each grep criterion to the files its ticket claims, not the whole tree. A pattern that also matches a pre-existing line in an unclaimed file fails for a reason the ticket cannot fix. 2026-10-17: a criterion matched a line in an unclaimed file and was narrowed to the claimed file before the worker reran it through `goal.mjs run`.
