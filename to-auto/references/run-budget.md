# To-auto run budget and stop conditions

Record every budget change as one commit together with its stop conditions, before any ticket runs under the new limit. Never cut a registered item to fit the time left: keep it registered and let the stop conditions decide what stays open. Splitting the objective into a second run, registered up front with every item owned, is not a cut (see Before choosing a budget).

## Recording a change

1. Append one line to the run log: `budget: <old> -> <new> (source: <who>)`. A budget set by a decision subagent is marked `not owner-approved`, unless the owner's own message delegated that decision to the named persona (for example "/kun will answer all questions"). Then the source reads `<persona> under owner delegation <date>`, counts as owner-approved, and the message is cited in the log.
2. Update the ledger's wall-clock line to the new ceiling and end time. Grep the new end time and require exactly one match. Take "now" from `date` on the system clock before deciding a cap, never from the ledger's own wall-clock estimate: the two diverged on 2026-10-17 and the cap decision was made on the wrong one.
3. Commit both files in one commit: `goal.mjs commit -m "[<slug>] budget ..." <log> <ledger>`. Read the sha back.
4. In the hand-back, name the budget, its source, and whether the owner approved it: no for a subagent decision outside a delegation, yes for one delegated in the owner's message.
5. A cap raise reopens the frontier. Tickets declared `stuck` only because the old cap was too short go back to `ready-for-agent` in priority order; stop conditions decide what stays open. Re-plan in the same commit as the budget line, not in a second commit later (2026-10-17 M4: 09/10 were pre-declared stuck for the cap at 15:0x, then re-planned at 15:24 under the extended cap, costing two ledger commits).

## Stop conditions to write with any budget

- Two failed fixes on one ticket with the same root cause: leave it open with a one-line named blocker and move on. The run does not stop for it.
- A wrap-up start time: fresh review, hand-back and retro start no later than it, whatever is still open.
- Timed benchmarks run only in an idle-machine window (see the `timed-benchmark-hygiene` skill, quiet-mac-timing reference). If none comes before wrap-up, mark them `blocked: no idle window` and continue with untimed tickets. Start a long timed arm only if it ends before wrap-up.
- A hard stop at the ceiling: open work stays open with its blocker named.
- Claim amendments and waivers are capped per ticket at one waiver and two amendments. A criterion still failing after the third amendment makes the ticket `stuck` with its blocker; its unmet criteria move to a new ticket. Count them in the retro budget line, e.g. `claim amendments: 02 1, 08 1, 10 2, 11 2 (+1 refused); waivers 1`.
- A quota stop is enforced only if quota can be read unattended. `quota-axi` reports Claude as `auth_required` (`keychain_prompt_required`, remedy `quota-axi --allow-keychain-prompt`), and that prompt needs the owner at the Mac, so an unattended run cannot pass it. Log `quota stop: not enforceable (credentials = blocker)` in the budget commit and keep the wall-clock stops. Check the quota once at 0d so the log says what was read.
- Size the wrap-up start from measured stage-8 length, not a fixed margin: take the previous runs' stage-8 wall clock (review, fixes, re-verify). A fixed two-hour margin left second-round fixes unverified at the hard stop (metal-proxy b4: stage 8 ran 23:44 -> 01:28, ticket 28 finished unlanded at 01:28 with a 01:45 stop). Fixes found late in stage 8 need their own re-verify slot before the hard stop, or they are reported unlanded in the retro. If the hard stop forces a shorter stage-8 than CLOSE.md names (for example two parallel fix tickets on disjoint claims instead of one fix subagent), log `deviation: <CLOSE.md step> → <what runs instead>, <why it fits the stop>` in the ledger in the same commit as the budget line, and name the single re-verification that covers both fix sets at the merged head.

## Before choosing a budget

Before the first dispatch, sum the serial GPU work and compare it with the hours left at the ceiling. Serial GPU work = per-ticket GPU-serial estimates from prior runs' receipts (B5 [M]: 32K feed + matrix ~45 min, 128K feed ~20 min, models tier ~30 min, check.sh ~5-6 min), plus the measured stage-8 length, plus planning that does not overlap. Count only the GPU-serial sum against the clock; CPU-only tickets overlap it. Write the sum and the comparison in the ledger with the budget line. If the sum exceeds the ceiling, split the objective into a second run registered up front, every item owned by exactly one run. Do not leave the gap for the stop conditions to find mid-run. If the work does not fit even after a split, say so in the report. Do not hide the shortfall by dropping a benchmark or results doc on purpose; that is pre-cutting. Pre-cutting also covers trimming a ticket to a 2K-only or smaller scope, or holding tickets open ("held open at budget") against a final-review start time the orchestrator chose; run the tickets in priority order and let the stop conditions decide what stays open. Say the shortfall in the report, and do not announce a cut as done.

A worker that stops a validation run to meet a wrap-up stop must not return `completed`. Its receipt reports that tier as not run, with the reason, and the orchestrator reruns it at the receipt head before landing (2026-10-11 metal-proxy b4 t10: the worker stopped the long-prompt spec tests "after 31 minutes to stay inside the 22:50 stop" and still returned `"conclusion": "completed"`; the orchestrator reran the tier at 613965a and it passed).
