# Plan: stages 1 to 6b

Stay in one context window through stage 6b when it allows: spec and tickets are primary sources for each other. Completion criteria per stage are in PIPELINE.md. All artifacts go to the control plane (CONTROL.md), committed after each stage; registry `status` moves `planning` → `specced` → `ticketed`.

1. **Route.** Explore the repo first, no external lookup: `CONTEXT.md`, `docs/adr/`, `docs/agents/*.md`, seams, test conventions, the failing command if one is named, and the tracker for overlapping work. Read ask-matt first (`node ROOT/scripts/matt.mjs resolve ask-matt`, the router at the pin), then walk FLOWS.md § Routing tree, which applies the autonomy overlay to the route ask-matt names; classify the objective as one of `bug`, `issue`, `refactor`, `upkeep`, `fog`, `greenfield`, `feature`. Output the route, an adopted-patterns list (each line naming its skill; open a skill's file before adopting any load-bearing claim about it), and a **research need** line per FLOWS.md § Research need: `research: none | targeted: Q1… | up-front`. Write `findings.md`: repo-sourced facts, numbered requirements R1…, and open external questions Q1… (one API, one behaviour, one version claim each). A `greenfield` classification switches to the `to-new` overrides (`ROOT/to-new/SKILL.md`); a `bug` classification arms the § Bug fast path below.
2. **On-ramp (conditional).** Run what stage 1 chose, self-answered per KUN.md: `triage` (raw issues), `diagnosing-bugs` (something broken; runs in the run worktree; loop goes red before any theory), `wayfinder` (fog; merges at stage 5 as `to-spec <map path>`; the local tracker template carries the "Wayfinding operations" section, verified; it spawns `research` per research ticket itself, through `research-stack`), `improve-codebase-architecture` (upkeep, no target), `zero-tech-debt` (refactor of a named area; its pre-flight and end-state paragraph seed the grilling). Skip for a plain feature. An on-ramp that meets an external unknown (a hypothesis naming third-party behaviour, a library contract the repo does not pin) appends it as Q<n> to `findings.md` and raises the research need to `targeted`.
3. **Research (conditional).** When the research need is `none` and `findings.md` has no open Q, log `research: skipped (no external unknown)` and continue. Otherwise load `research-stack` now (first use in the run; keep its route table in context; every later lookup in every stage and subagent goes through it) and call `research` once per open Q with that one narrow question; its brief says it is already the research subagent and spawns nothing. Append sourced facts to `findings.md`, close each Q, promote settled facts to R<n>. Any later stage or subagent (a grilling round, an implementer, the review) that hits an external unknown does the same on demand: load `research-stack` if not yet loaded, one `research` call, one line in `log.md`. No "TBD" survives past this stage.
4. **Grill.** Load grill-with-docs (it calls `grilling` and `domain-modeling`; confirm both loaded). Run the rounds with KUN.md § Grilling rounds (answerer + challenger subagents, both working in the run worktree). Facts a round needs come from sub-agents, not questions. For each new module or seam call `codebase-design` and run design-it-twice. For every module the objective touches call `defensive-design` in Design mode once: consequence tier 0–3, contract, smallest proportional controls in a failure→consequence table; Tier 2/3 get its checklist sections and, at any security-sensitive boundary, the secure-coding overlay. When the deliverable is a skill or an agent-facing doc, call `writing-for-agents` as the standard. When only a named person could answer, load to-questionnaire, write the file, continue with the default. Terms into `CONTEXT.md` as they settle, committed as their own commit `[<slug>] glossary` at the head of the run branch so cross-run merges conflict only there (the report lists glossary deltas); an ADR only when hard to reverse, surprising, and a real trade-off. Name the test seams (highest existing seam, ideally one).
   **4b. Challenge gate.** Done when the frontier is empty, every answer in `log.md` is `(source: kun)` or `(source: default, contested)`, and `CONTEXT.md` changed on disk (or evidence-backed log that domain context required no change; do not manufacture no-op edits).
5. **Spec.** Load to-spec. Synthesize from stages 1 to 4 only. Seams into Testing Decisions; the defensive tier and controls table per module into Implementation Decisions; the tier's required tests (malformed input, negative authorization, duplicates and races, cancellation and restart, as applicable) into Testing Decisions. Publish to the tracker from stage 0b (local `.worktrees/control/tracker/<feature-slug>/spec.md`, `ready-for-agent`); keep the copy at `.worktrees/control/runs/<slug>/spec.md`.
   **5b. Reconciliation gate.** A subagent with only `log.md`, `findings.md`, and the spec lists every logged answer and requirement that is missing from the spec or softened (a number became "reasonable", a negative requirement became silence, an ordering guarantee became prose). Fix the spec for each; re-run the gate until the list is empty. Log the gate's output.
6. **Tickets.** Load to-tickets, pointed at the spec path. Local tracker: one file per ticket, numbered blockers-first. Every ticket carries a demo-path line, its module's defensive tier, and a **claims** list in three classes (CONTROL.md § Tracker grammar): `exclusive` paths it will create or modify; `shared-regenerate` files every ticket touches through a tool (lockfile, codegen output, snapshots, registries) which the merger regenerates with the `commands:` regenerate entry instead of treating as a conflict; `guarded` paths (CI workflows, top-level config, migrations) which require explicit user capability grant or objective authorization (a persona cannot grant guarded-path authorization on its own). Derived from the stage 1 exploration and the spec's module list; in a monorepo, prefixed by package. Prefactoring tickets are scoped with `zero-tech-debt` (pre-flight, one coherent end state) and come first. Self-quiz (granularity, edges, merge/split) via KUN.md. Strip `ready-for-agent` from the parent spec after publishing.
   **6b. Criteria and claims gate.** For every acceptance criterion describing new behavior or bug fixes, name the observation that would show it false and confirm it fails at the base commit (run it with the test patch against base; a missing test file is not behavioral red). Criteria asserting preserved invariants, security guarantees, or existing compatibility must remain green at base; do not rewrite or invert valid invariants to force a red result. For every pair of tickets, intersect their `exclusive` claims (shared-regenerate never conflicts; guarded needs explicit capability grant); overlapping tickets get a blocking edge or a merged scope. Every ticket that enters the graph later (a bug ticket from BUILD.md) passes this same gate before it can be `ready-for-agent`. Write the ticket table (blockers, claims, status `blocked`/`ready`) into `todo.md`. Done when no new-behavior criterion is green at base, preserved invariants remain green, and no two unordered open tickets share an `exclusive` claim. Local tracker: `node ROOT/scripts/goal.mjs frontier <feature>` exits 0 (no malformed ticket, no overlap). GitHub tracker: check the same two rules over the issues' Status, Blocked-by, and Claims lines.

## Bug fast path (route `bug`)

Applies when `diagnosing-bugs` finished with: one command red before any theory, a regression test red then green, a named seam, a post-mortem, and the fix confined to modules that fit one `exclusive` claim set at Tier 0 or 1. Then stages 4 to 6 are skipped:

- `spec.md` is the post-mortem: symptom, red command, root cause, seam, regression test path, tier, files touched. Publish it to the tracker as the parent.
- Exactly one ticket `01`: acceptance criterion = the regression test command; demo path = the red command going green; claims = the files the fix touched; tier from `defensive-design` Implement mode over the diff. Run the 6b gate (the criterion is red at the base commit by construction; verify by running it there).
- Stage 7 has nothing to dispatch: record ticket `01` as merged with the commit range the on-ramp produced on the run branch, run the full suite against the per-test baseline, tick the ticket, and go to stage 8 (where final review diffs against the immutable `review_base` captured at stage 0c, ensuring the stage 2 fix is fully reviewed).

Any of these turn the fast path off and the run continues at stage 4 with the post-mortem as its first finding: no seam found, more than one claim set, Tier 2 or 3, a `guarded` path, the regression test needs a fixture the repo lacks, or the post-mortem names a design cause (`improve-codebase-architecture` lead). `/to-bug` pins this route and skips the classification.
