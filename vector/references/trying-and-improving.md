# Try the workflow and make the next run better

Read this when the person asks to try or run an agreed VECTOR workflow. A request to design a workflow alone does not start its operational steps.

## Start with a small real example

Use one supplied example or a manageable batch within the person's request. Reuse valid permissions already given. Confirm only missing information or decisions that materially affect the task; do not restart the six questions if they are already answered.

If the person wants to try a draft, create and check the draft. Do not silently turn the trial into sending, ordering, changing accounts, publishing, or scheduling. When those actions are expressly part of the authorized task, proceed within their agreed limits.

Use the tools and information actually available. If a connection is missing, prepare everything possible and explain the smallest next step, such as providing a document or having the responsible person complete one action. Do not claim to have read an inaccessible source.

## Check the result

Compare the output with the agreed checks and original source material. Involve the named person where judgment or review is part of the workflow. A check that cannot be performed remains unfinished; do not label it passed.

Keep the report simple: what is ready, what needs correction or a decision, and the next action. Record enough source references to resolve a disagreement without filling the user's answer with process details.

## Handle problems without making them worse

- If a fact is missing or sources conflict, identify it and follow the agreed fallback. Do not fill the gap with a confident guess.
- If a result fails a check, correct it and check again, at most twice. Return a problem that survives both corrections to the person.
- If a tool has a temporary problem, retry at most three times with a growing wait (for example 10, 30, then 90 seconds). Invalid input, denied access, and a missing human decision are not temporary: report them on the first failure.
- If a send, purchase, or other change has an uncertain outcome, check whether it actually happened before attempting it again. If you cannot establish the outcome, explain the uncertainty and hand it over; avoid duplicate actions.
- Record each completed send, order, or change in the run notes as it happens, with whatever identifies it (a message link, order number, or file path). If interrupted, retain the completed work and identify the next unfinished step. Recheck changeable information and those records before resuming, so a restart never repeats a completed action.

Keep detailed operational notes only where they are needed. Explain problems to a non-technical person in terms of the work and its effect.

## Learn from the person's corrections

After a completed trial, cover these questions naturally, one at a time if needed. In an [unattended run](../SKILL.md#unattended-runs), list them as owner questions instead:

1. Did the result meet the checks we agreed?
2. What did you have to change or do yourself?
3. What should we keep or change for next time?

Compare human effort before and after, including review, corrections, and maintenance. Keep elapsed waiting time and setup effort separate where useful. Describe estimates as estimates; claim savings only when there is evidence. If the new workflow is more trouble than it is worth, simplify it, delegate a smaller part, or keep the old approach.

Propose a small, specific memory update grounded in the correction: for example, “Use three sections: progress, concerns, next steps” or “Mark missing team updates; do not carry last week's progress forward.” Avoid turning a one-time exception into a universal rule.

## Keep useful notes honestly

Separate reusable guidance from temporary unfinished work. For reusable notes, keep the accepted instruction or example, why it matters, who maintains it, and when it should be refreshed. For an unfinished task, keep only its current status, relevant references, uncertain actions, and next step.

Use the approved place and permissions already established. Where a new shared destination or a new audience would change who can see the information, resolve that specific decision first. Do not store credentials or unnecessary personal data.

Confirm a supported save before saying notes are saved. If no persistent place is available, give the person a short note to copy next time and explicitly say it has not been saved. A suggestion for what to remember is not proof of permanent learning.

## Close the trial

State what was actually done and checked, what remains, the agreed improvement for the next run, the next owner/date when known, and the memory's save status. Suggest a follow-up review when useful, but do not create calendar events, recurring jobs, or messages unless requested.
